# Magic Cards Example Pipeline

This example demonstrates how to generate an entire Magic: The Gathering card set using ArtGen's pipeline system. It showcases most of the advanced features — dynamic asset creation, research steps, conditional execution, human-in-the-loop selection, AI assessment, and a final compilation step.

## Running It

```bash
artgen run examples/magic_cards/magic-cards.yaml
```

Or via the web GUI:
```bash
artgen web
# Then open the pipeline from the UI
```

## How the YAML Works

### Top-Level Structure

The pipeline YAML has five main sections:

```yaml
name: "Shadows of Valdris"       # Pipeline name (used in logs and state)
version: "1.0"                    # Version string (triggers cache invalidation on change)
description: |                    # Human-readable description
  A 50-card Magic-style set...

types:     # Data type definitions
context:   # Global variables
assets:    # What we're producing
steps:     # The pipeline DAG
```

### Types

Types define structured data schemas for assets — like dataclasses. Field types include `text`, `image`, `number`, `boolean`, `list`, enums (`a | b | c`), and optional fields (`type?`).

```yaml
types:
  MagicCard:
    name: text
    rarity: common | uncommon | rare | mythic
    power: number?              # Optional — only for creatures
    art: image?                 # Will be generated by the pipeline
```

Types are used for validation and to give the pipeline system knowledge of your data structure. Fields marked with `?` are optional and can be left empty or filled in by later steps.

### Context

Global key-value pairs accessible from any step via `{context.key}`:

```yaml
context:
  setting: "Gothic horror, crumbling cathedrals, haunted forests"
  card_count: 50
  distribution:
    common: 25
    uncommon: 15
    rare: 8
    mythic: 2
```

Context is automatically included in LLM prompts to maintain consistency across all generation steps.

### Assets

Defines *what the pipeline produces*. Assets can be:

- **Inline items** — listed directly in the YAML
- **From an external file** — `from_file: ./cards.csv`
- **Dynamically generated** — created by a pipeline step

This example uses dynamic generation:

```yaml
assets:
  type: MagicCard
  generated_by: design_cards    # The step that creates the card list
```

The `design_cards` step runs first, outputs a list of cards, and those become the assets for all subsequent `for_each: asset` steps.

### Steps

Steps form a directed acyclic graph (DAG). Each step declares its dependencies via `requires`, and the pipeline engine runs steps in parallel when possible.

#### Step Properties

| Property | Description |
|----------|-------------|
| `id` | Unique identifier, used to reference this step's output |
| `type` | What kind of step: `research`, `generate_text`, `generate_image`, `assess`, `user_select`, `user_approve`, `custom`, etc. |
| `requires` | List of step IDs that must complete before this one runs |
| `for_each: asset` | Run once per asset (otherwise runs once globally) |
| `condition` | Expression that must be true to run (e.g. `"asset.rarity in ['rare', 'mythic']"`) |
| `config` | Type-specific configuration |
| `cache` | Caching behavior: `true`, `false`, or `skip_existing` |

#### Template Variables in Prompts

Prompts use `{namespace.field}` syntax to reference data:

- `{context.setting}` — global context values
- `{asset.name}` — current asset's fields
- `{step_id.output}` — output from a previous step

## Pipeline Walkthrough

### Phase 1: Set Design (Global Steps)

These steps run once for the entire set — they aren't per-card.

1. **`research_mtg`** and **`research_art`** — Two `research` steps that run *in parallel* (no dependencies between them). They gather information about MTG design and art styles respectively.

2. **`brainstorm_mechanics`** — Takes the research output and brainstorms new keyword mechanics. Uses `variations: 2` to generate multiple options.

3. **`select_mechanics`** — A `user_select` step. The pipeline pauses here and presents the brainstormed mechanics to the user. They pick 3-4 to use for the set.

4. **`style_guide`** — Creates an art direction guide based on the art research. Runs in parallel with brainstorming (it only needs `research_art`, not `research_mtg`).

5. **`design_cards`** — The critical step. Uses the selected mechanics and context to generate the full card list. Its output *populates the asset list* (`generated_by: design_cards`), creating the cards that all subsequent per-card steps will iterate over.

### Phase 2: Per-Card Generation (Parallel Per-Asset Steps)

Each of these steps runs once per card, in parallel across all cards:

6. **`card_abilities`** — Writes abilities/rules text for each card, using the selected mechanics.

7. **`card_flavor`** — Writes flavor text, informed by the abilities and setting.

8. **`art_prompt`** — Creates a detailed image generation prompt using the flavor text and style guide.

9. **`card_art`** — Generates card art images. Uses a conditional `variations` count — rares/mythics get 4 variations, commons/uncommons get 2:
   ```yaml
   variations: "4 if asset.rarity in ['rare', 'mythic'] else 2"
   ```

10. **`assess_art`** — AI vision assessment. Evaluates each generated image against criteria (matches concept, fits aesthetic, good composition, no artifacts). Cards scoring below `threshold: 0.7` are automatically retried up to 2 times.

11. **`approve_art`** — Human approval gate, but *only for rares and mythics*:
    ```yaml
    condition: "asset.rarity in ['rare', 'mythic']"
    ```
    Commons and uncommons skip this step entirely.

### Phase 3: Compilation (Gather Step)

12. **`compile_set`** — A `custom` step with `gather: true`. It waits for *all* per-card steps to finish across *all* assets, then runs a user-defined Python function to compile everything into final deliverables (set JSON, card images, print sheets).

## Key Concepts Demonstrated

### Dependency-Driven Parallelism

Steps without dependencies between them run in parallel automatically. In this pipeline:
- `research_mtg` and `research_art` run simultaneously
- `brainstorm_mechanics` and `style_guide` run simultaneously (they depend on different research steps)
- All per-card steps run in parallel across cards

### Dynamic Asset Creation

Instead of listing all 50 cards upfront, the pipeline generates them:
```yaml
assets:
  type: MagicCard
  generated_by: design_cards
```
This lets the AI decide what cards to create based on the research and selected mechanics.

### Conditional Steps

The `approve_art` step only runs for rare and mythic cards:
```yaml
condition: "asset.rarity in ['rare', 'mythic']"
```

### Gather Operations

The `compile_set` step uses `gather: true` to wait for all parallel per-card work to finish before assembling the final set.

### Caching & Resumability

Every step's output is saved to `.artgen/`. If the pipeline is interrupted (or you want to tweak a prompt), you can resume without re-running expensive steps. The `cache: skip_existing` option is especially useful for per-asset steps — it skips cards that already have output.

## Adapting This Example

To create your own set:

1. Change the `context` values (setting, card_count, distribution)
2. Adjust the prompts to match your theme
3. Modify the `MagicCard` type if you need different fields
4. Add or remove steps as needed

For a working production version of this pipeline, see `pipelines/mtg-generator/pipeline.yaml` which includes additional phases for mechanic brainstorming, card critique/refinement, and full card rendering via Magic Set Editor.
